<h2 id="visualization">Visualization and organization</h2>

Atlas transforms records in the browser using Three.js and a TanStack Charts extension. Your backend sends company data; it does not need to calculate positions or geometry.

| Feature | How it works |
| --- | --- |
| Districts and intersections | Up to three distinct categories form up to seven combinations. Each company appears exactly once. |
| Buildings sized by metric | `metric.value` controls size; its label appears in details and tooltips. |
| Visual health | `healthy`, `warning`, and `critical` identify health states. Risk effects can be disabled. |
| City life | Cars, pedestrians, traffic lights, and vegetation complete the scene. |
| Rendering | Instanced geometry is reused for buildings, windows, vegetation, traffic, and particles. |

<h2 id="interaction">Navigation and interaction</h2>

Drag with the left mouse button to rotate horizontally, use the wheel or a pinch gesture to zoom, and use the right mouse button or two fingers to pan. Switch between isometric and top views. Press `0` to restore the overview.

Search finds companies by name. Selecting a building opens its details and emits `onSelect`. Fullscreen requests a Screen Wake Lock, when available, to keep the display awake. Exiting fullscreen, hiding the tab, or unmounting releases the lock. Optional automatic rotation pauses during interactions.

Map controls follow the browser's language: `pt-BR` or `en-US`, with English for other locales. Supplied names and labels are preserved. Reduced-motion preferences disable particles and reduce animations. The 3D scene requires WebGL.

<h2 id="weather">Weather API integration</h2>

**In the Atlas application**, `useWeather` queries Open-Meteo while **City life** is enabled. **In the `atlas-city-chart` package and this playground**, the map receives a `weather` prop and does not query weather services or request geolocation. The playground's selectors simulate the environment locally.

### 1. Location and request

The application requests location without high accuracy, with a **10-second** timeout, over HTTPS or localhost. Latitude and longitude are rounded to **two decimal places**. Coordinates and cached results stay in memory; they are not written to cookies, `localStorage`, or company records.

The client sends a GET request to `https://api.open-meteo.com/v1/forecast` with `credentials: "omit"` and these parameters:

```text
latitude=-23.55
longitude=-46.63
current=weather_code,rain,showers,snowfall
timeformat=unixtime
forecast_days=1
```

These coordinates are illustrative. The application uses the approximate location authorized by the visitor. The provider receives the connection's IP address and the submitted coordinates.

### 2. Response and interpretation

The adapter reads `current.time` in Unix seconds, `weather_code`, `rain`, `showers`, and `snowfall`. It rejects incomplete responses, unrecognized codes, negative precipitation values, and timestamps more than **90 minutes** away from the client's clock.

| Condition | Scene result |
| --- | --- |
| Positive snowfall or a snow code | `snow`, taking priority over rain. |
| Positive rain + showers or a rain code | `rain`. |
| Neither condition applies | `none`. |

Effects represent a regional estimate. Rain includes particles and simulated lightning; flashes do not indicate actual lightning detection. Rain particle counts scale with city area, capped at 800, so smaller examples do not receive the same number of drops in less space. Snow gradually adds a partial layer to the ground and rooftops while the simulation is active.

### 3. Cache, refreshes, and failures

| Situation | Application behavior |
| --- | --- |
| Successful request | Keeps results in memory for 15 minutes. |
| Hidden tab | Pauses new refreshes and checks on return. An in-flight request may still finish. |
| Slow API | Cancels the request after 10 seconds. |
| Network failure or invalid response | Removes precipitation, displays an unavailable message, and retries after 15 minutes. |
| Permission denied or location unavailable | Keeps the map working without precipitation and displays the reason. |
| Permission revoked | When supported by the Permissions API, clears coordinates and cache and cancels the request. |
| City life disabled | Cancels requests and timers, pauses particles, and restores daylight. |

Re-enable **City life** to request location again. A still-valid cache may be reused. Manual environment selectors override the scene, but automatic requests in the application continue to follow the **City life** setting.

### 4. Custom endpoint

Configure the endpoint when building the **Atlas application**:

```sh
VITE_WEATHER_API_URL=https://weather.example.com/v1/forecast npm run build
```

The service must accept the parameters above, return the [Forecast API](https://open-meteo.com/en/docs) `current` contract, and allow CORS for your application origin. `VITE_*` variables are public in the bundle: add private keys on a backend, never in the client URL.

If your project uses only the package, connect your own provider and pass the converted weather state:

```jsx
<CityMap
  data={companies}
  weather={weatherState.type} // "none", "rain", or "snow"
  lightingMode="auto"
/>
```

`weatherState` belongs to your application's integration. The Atlas hook and adapter are implemented in [`use-weather.js`](https://github.com/raphox/atlas/blob/main/src/hooks/use-weather.js) and [`weather.js`](https://github.com/raphox/atlas/blob/main/src/weather.js); they are not package exports.

Open-Meteo data uses [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). Preserve provider attribution when displaying its data. Service access terms are separate from the data license: check the [Open-Meteo terms](https://open-meteo.com/en/terms), including commercial eligibility and request limits, before operating an instance. The free endpoint is intended for noncommercial use; commercial deployments need a compatible service. This documentation's playground uses simulation only.

<h2 id="lighting">Lighting and simulation</h2>

Automatic lighting follows the browser's local clock independently of the weather API: sunrise from 6–8 a.m., day from 8 a.m.–5 p.m., sunset from 5–7 p.m., and night at other times. Selectors let you combine day, sunrise/sunset, or night with rain, snow, or no precipitation.

[Try the weather example in the playground](./#playground).

<h2 id="monitoring">Monitoring and application data</h2>

In the Atlas application, the table, filters, and pagination stay synchronized with the city. Filter by health or categories, search companies, and display 100, 250, 500, 1,000, or all companies per city. Filters are applied before pagination.

The monitoring panel shows a local clock and up to four companies currently at high risk, ordered by the start of their current status (`statusChangedAt`), using the full dataset. Records without that timestamp are counted separately. The panel reflects the latest load or import; company records are not polled automatically.

JSON imports up to 5 MB are validated in the browser and do not persist after reload. An invalid import preserves the previous city. To connect a backend, set `dataUrl` and `mode` in `public/config.json`; the endpoint can return an array or `{ companies: [...] }`. This flow belongs to the application. The reusable package receives records through `data`.

<h2 id="integration">Integration and distribution</h2>

The package provides plain CSS and Tailwind 4 themes, callbacks, and an imperative camera API. It can render an SSR shell, but WebGL starts only in the browser. In frameworks with Server Components, place the map inside a client boundary.
